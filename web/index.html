Distributed Smart Parking

Parking sensors, lot servers and a driver app, each a separate process that only communicates by messages. Each lot server owns one lot. There is no central coordinator. Processes can be killed, links cut and replies lost; the rest keeps working.

Milestone 2

Communication

TCP sockets, one JSON envelope for every message (4-byte length header, UTF-8 body), and three patterns: request-reply, publish-subscribe and group communication. Two new processes: a broker and a registry.

Who connects to whom

Each arrow is a TCP connection. Solid ones stay open, dashed ones are opened when needed. A lot server is a service to clients, a subscriber and publisher at the broker, and a member of the lot_servers group.

sensor node broker :5000 lot server registry :5010 client

One exchange per connection

Connect, REQUEST, REPLY, close. The REPLY carries the request's msg_id in reply_to. If nothing comes back in 2 s the client reconnects and sends the same REQUEST again. The service caches replies by msg_id, so the retry gets the cached reply and nothing runs twice.

Unknown op or bad args: status: ERROR. No reply after 3 tries: ServiceUnavailable, written to the log.

Broker in the middle

Subscribers keep one long-lived connection to the broker. A PUBLISH becomes one EVENT per subscriber, sent on that subscriber's connection and logged once per delivery. The publisher gets an ACK with the delivered count. A subscriber that cannot be reached is removed from the topic.

Limits: the broker is a single point of failure, and a slow subscriber delays the others.

Membership at the registry

Members JOIN a group at the registry. To send, a node asks for MEMBERS, then opens one connection per member and sends GROUP_MSG, one log line per target. An unreachable member is logged and skipped. The others still get the message.

No ordering or atomic delivery. Membership can change during a send. Future work: total ordering, acknowledgements, multicast.

Message envelope

Every message is a JSON object with these fields, sent as a 4-byte big-endian length followed by the UTF-8 body.
fieldmeaning
typewhich kind of message; the receiver dispatches on it
msg_idunique id; a REPLY or ACK carries the id it answers in reply_to
senderprocess name, for the logs
timestampISO 8601 with milliseconds, sender's clock, used as ordering evidence
payloadtype-specific data
A bad length header, truncated body or non-JSON bytes raise ProtocolError and the connection is closed. A socket closed mid-read raises ConnectionClosed. Max message size 1 MB.

Milestone 3

Peer-to-peer overlay

The lot servers form an unstructured mesh. Each one keeps a short neighbor list, joins through any running peer, gossips its own summary, keeps replicas of the other lots, and floods a lookup for anything it does not have. There is no coordinator and no rule that says which node owns which key.

Software stack on each lot server

Sensor updates and client requests never deal with routing. The application only calls three functions.
Applicationspace table, find, reserve, release, summary every 3 s
Middlewareput(key, value)   get(key)   lookup(key, ttl)   aggregate()
Overlayneighbor list, join and leave, ping repair, gossip, flood, convergecast
Transportframed JSON over TCP, one port per lot (Milestone 2)
Replicas take load off the owner: a client asking lot A about lot C is answered from A's copy, so only reservations have to reach C. That keeps the arrival rate at each lot below its service rate during a spike.

How long is a cached count valid?
Every replica records when it was stored. find reports its age and flags it stale after 12 s, four missed gossip rounds. Clients see an old number labelled as old.

            
When do updates become visible?
Neighbors see a put within one message. Everyone else in the same round with probability 1 − (1 − pf)n, otherwise within the next round (3 s) or the next ping (5 s), whose answer carries the full table.

            
How are competing updates handled?
Only the owning lot writes its key, and every write carries a version. A replica keeps a value only if its version is higher. Late or duplicated rumors cannot roll it back. Reservations always go to the owner.

          

        

      

      

        

          
Five lots on the real system

          
Console lines from the prototype: four lots start, E joins through C and receives four replicas at once, D floods a lookup for B, C leaves, D is killed.

          
After C leaves, B and E are each down to one link. The random sample in the next ping answer lets them find each other, so the mesh stays in one piece.

        

        

          
Nine new message types

          
All of them use the Milestone 2 envelope and arrive on the lot server's normal port. JOIN, NEIGHBOR and PING are answered with an ACK on the same connection. The rest are one way.

        

        

          
Every lot is a cache

          
Each server holds the other lots' summaries, so it answers questions about them without asking. The system is eventually consistent: there is no moment when every lot agrees exactly, but each copy says how old it is.

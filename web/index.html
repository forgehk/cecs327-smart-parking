Distributed Smart Parking

Parking sensors, lot servers and a driver app running as separate processes that only talk by sending messages. Each lot server owns its own lot; there is no central coordinator. The system keeps answering when a sensor dies, a server crashes, a link is cut or a reply gets lost, and every message is logged so you can see what happened.

Team: Degoma, Gonzalez-Morales, Karakra, Lee, Lopez, Nguyen, Ocegueda

Two drivers, one space

alice reserves a space, bob tries the same one and gets DENIED. One request-reply at a time per lot server.

Milestone 2

Communication

The simple messages above are replaced with a real communication layer: TCP sockets, every message a JSON envelope sent as a 4-byte length header plus UTF-8 body, and three patterns — request-reply, publish-subscribe and group communication. Two new processes appear: a broker and a registry. Every process logs every message; a crashed lot server replays its log.

prototype/comm · MESSAGES.md · tests · sample logs

Who connects to whom

Every arrow is a TCP connection carrying framed JSON. Solid links stay open, dashed ones are opened on demand. A lot server plays four roles at once: service to clients, subscriber and publisher at the broker, and member of the lot_servers group.

sensor node broker :5000 lot server registry :5010 client

One exchange per connection

Open, REQUEST, REPLY, close. The REPLY echoes the request's msg_id in reply_to. If no reply arrives within 2 s the client reconnects and resends the same REQUEST. The service caches replies by msg_id, so the retry gets the cached answer and the reservation is never made twice.

Failure cases: unknown op or bad args → status: ERROR; no reply after 3 tries → ServiceUnavailable, logged.

Broker in the middle

Subscribers keep one long-lived connection to the broker. A PUBLISH is fanned out as one EVENT per subscriber on that subscriber's own connection, one log line per delivery. The publisher gets an ACK with how many subscribers were reached. A subscriber the broker can't deliver to is dropped from the topic rather than retried.

Limits: the broker is a single point of failure; a slow subscriber can delay the others.

Membership at the registry

Members JOIN a group at the registry. To send, the sender asks for MEMBERS, then opens one connection per member and sends GROUP_MSG, logging one line per target. An unreachable member is logged and skipped; the others still get the message.

No ordering or atomic delivery is guaranteed, and membership can change during a send. Future work: total ordering, acknowledgements, multicast.

Message envelope

Every message, in every pattern, is a JSON object with these fields, sent as a 4-byte big-endian length followed by the UTF-8 body (struct.pack("!I", len)).
fieldmeaning
typewhich kind of message; the receiver dispatches on it
msg_idunique id; a REPLY or ACK carries the id it answers in reply_to
senderprocess name, for the logs
timestampISO 8601 with milliseconds, sender's clock, used as ordering evidence
payloadtype-specific data
Malformed input: a bad length header, a truncated body or non-JSON bytes raise ProtocolError and the connection is closed; a closed socket mid-read raises ConnectionClosed. Max message size 1 MB.
